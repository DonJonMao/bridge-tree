## 为什么变成 49 / 75 个来源的硬义务

- call3 看到 49 个 source spans、6 个 documents，返回两条 unresolved。call4 看到 75 个 spans、9 个 documents，仍返回同样两条缺口（无序文本 hash 完全相同）。
- `joint_reading.py:1992–1997` 的实际实现：由于 `slot.unresolved` 没有逐项引文映射，任何 unresolved 都绑定本次全部 visible sources。义务 ID 由变量、scope 和这组 sources 决定。
- 因此 call3 生成的 49-source 义务在 call4 被原样提供；call4 保留缺口时，又生成 75-source 义务。repair5 同时提供这两个 ID；描述相同，来源窗口不同。已逐项核实两组 source aliases 正好等于各自完整窗口，call4 的前 49 个完整 spans 与 call3 一致。
- 这些计数代表必须重新审阅的来源出处集合，不代表已证明存在 49/75 个独立必要历史条件，也不等于需要读取全库。来源集合包含整窗，因此不能把每个 source 都视作 support 的必需前提。
- `joint_reading.py:1963–1986` 要求显式 offered ID、原始来源可见、无 unresolved/partial，并通过有来源的 settled reviews 覆盖原义务全部 sources，才能解除。该实现没有独立的逐缺口“是否为终端必要前提”语义裁决。
