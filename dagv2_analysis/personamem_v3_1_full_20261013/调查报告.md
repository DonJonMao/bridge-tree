# PersonaMem v3.1 失败与有效作答质量调查

2026-10-13。对象是 `dagbt/`、部署配置 `residual-memory.personamem16k.json`、方法 `original` 与 `dagbt_residual_memory_v1`。本次做日志分析与离线复现，没有修改生产代码或调用模型。

结论：当前差距包含两部分。第一，206/445 次失败中既有明确的代码/协议缺陷，也有任务规划无法完成、模型主动弃答和审计发现矛盾。第二，在双方都有效的相同题目上，确有质量下降，而且净差集中于把个性化回应任务处理为单变量事实认证的路径。旧 HotpotQA 的共同成功题增益确实存在，但新旧之间变化远多于 reranker，现有证据不能把下降单独归因于取消 reranker。

共同有效集合上：双方都对 127 题，双方都错 59 题；original 对而 residual 错 35 题，反向 17 题。因此有效作答净少答对 18 题。

### 质量下降集中于何处

按 residual 实际完成路径，在共同有效集合中分组：

| residual 完成路径 | 相同题数 | original | residual | 净少答对 |
| --- | ---: | ---: | ---: | ---: |
| `certified_symbolic` | 51 | 36/51 = 70.59% | 20/51 = 39.22% | 16 |
| `semantic_assessment` | 187 | 126/187 = 67.38% | 124/187 = 66.31% | 2 |

51 个符号认证成功题的表达式根节点全部为 `op=var`；48 题的 program 只有一个变量。这一批认证主要是在验证某个抽取值及其来源，不能视为对“最终选中的个性化回应合适”的形式证明。分组不是随机实验，不能把两个组之间的分数差解释为模式的因果效应；但它非常明确地指出了优先排查位置。

按题型看，共同有效题中的最大损失为 `recall_user_shared_facts`：53 题 original 38 对、residual 26 对；`suggest_new_ideas` 为 39 题 16 对比 10 对。也存在收益：`recalling_the_reasons_behind_previous_updates` 的 37 题为 30 对比 33 对；并非所有题型都退化。

## 206 次失败：可确证的运行机制

| 发布状态 | 数量 | 已确认的分层 |
| --- | ---: | --- |
| `budget_exhausted` | 107 | 97 次 ANN 耗尽；10 次 LLM 到达审计预留线 |
| `invalid_output_format` | 48 | 34 次终端返回 null；14 次已有合法字母，但语义值一致性检查未通过 |
| `unresolved_or_exhausted` | 23 | 11 次确定态被不兼容输出契约堵住；另 1 次规则未声明完整；其余仍不确定 |
| `audit_incomplete` | 17 | 10 次语义冲突/未知/未解决条件；7 次重复 ID、类型、容量或预算问题 |
| `execution_failed` | 7 | 全部记录为规划协议校验异常，见下文 |
| `timeout` | 4 | worker 超过 3600 秒；包内无这些题的部分执行轨迹，不能进一步确定耗时根因 |

### A. 97 次 ANN 耗尽主要不是 JSON 修复循环

97 次 ANN 耗尽中，94 次没有 failed slots；这些题仍有 LLM 配额，96 次没有走到语义终端组合。盲目加 LLM 次数无法解决这组现象。

对按日志体积选取的 6 个不同流程样例进行逐条阅读，看到这些模式：

- `1d914339-dec5-4e6d-90e2-881c5ca505fc`：已经读出用户阅读偏好，却把“近五年值得推荐的新书”定义成必须从个人历史里检索并证明的前置变量。
- `6defbf8e-0c2e-42f6-99e0-809ec183852e`：已经读出兴趣，但继续要求从个人记忆库找到当前可报名的 workshop。
- `89393cad-6d64-438d-a897-d0784d7eb3b1`、`7f7c4177-a11b-4a29-add6-b78ff733799c`：把用户关于做菜、打包的陈述，变成必须查清菜名/文化或完整物品清单的事实问答；当前读取内容没有满足这些细节。
- `bf1209ec-2d77-4385-be78-04abfba82f31`：同一集合变量累积 60 条支持观测，留下 6 个不同的完整集合值；系统按互相冲突处理，始终不绑定。这里有证据，问题是集合含义与状态协调。
- `3315a6fd-fcc2-4101-8766-f6b01d457713`：过去与现在的态度存在冲突，最终摘要虽有值，情绪变量仍 pending。

这些是任务拆解、知识库能力边界和冲突处理的证据，不是对全部 97 题的逐题根因统计，也没有证明整个可见历史中绝无相关内容。PersonaMem 没有 gold supporting documents，不能从错误答案直接推导检索 recall。

### B. 10 次 LLM 耗尽存在重复无进展处理

10 个病例均重复出现相同 reasoning response reference，执行了 16–22 次 `semantic_compose`。缓存重放会计入逻辑预算，因此重复 reference 不等于重复向服务发出 HTTP 生成。

- `26e1084c-2235-4dd6-9637-4f7b8990ac37` 后续 15 个批次没有可见来源，反复遇到 `Supported/counter observation needs original sources`。
- `0a90b38b-9bdf-437b-a4ee-fb671162c430` 没有 failed slots，但同一无答案结果被反复重放；模型一直说明缺少昨日 film blog post 内容。

`JointReader.read` 的 `progressed=True` 可以仅表示处理了批次，不代表事实、义务或可用证据有实质进展；控制器没有充分区分这两种情况。应基于状态/新证据变化限制重复动作。不能通过清空未解决义务、抹去反证来制造“成功”。

### C. “格式失败”包含终端语义接口缺口及类型错误

48 题全部没有 failed slots，41 题已完成审计，且 LLM 仍余 12–22 次。不是都因为模型输出了非法选项字符。

34 题的终端选项为 null；协议本来允许不确定时弃答，需分别分析任务错配或证据不足，不能全部当作 parser bug。

14 题给出了合法 a/b/c/d，但 `semantic_answer` 与最终检查的事实值不同。例如 `27b61c09-e5ab-4d00-b395-eea8ee619b70` 的一个字段是面向用户的回复，另一个字段是事实摘要。晚期一致性检查拒绝它是合理的；接口问题在于重复字段的语义没有在读取阶段统一检查并有界修复。

还有确定的表示缺陷：4 题生成的是 JSON 对象，发布侧却拿该对象的 JSON 字符串参与比较。`sync_nodes` 用 `display` 生成展示文字，`publish` 随后与原始 typed value 比 digest，导致同一值的不同表示被视为不一致。干净例子 `e0961881-e2b5-4e54-b370-aa6b4d533df9` 已有合法 c、审计完成，把发布字符串 `json.loads` 后与原对象完全相同。其余 3 例还同时存在 null 选项，因此修复这一点不等于挽回 4 个正确答案。

### D. 规划校验接受了不可能认证的组合

23 个 unresolved 中，12 个无 rule_binding 的静态计划把 `one_reason` 或 `all_failures` 与 `expression.op=var` 配对。原 `certify_output` 要求根操作分别为 `one_reason` 或 `failures`，否则直接返回 None，而规划接收阶段没有检查这种配对。这些专用运算处理布尔条件的失败见证，不是一般自然语言“一个原因/多个原因”的别名。

其中 11 题已经事实确定、没有 pending 变量，`possible_outputs` 清空 active demands，但无法认证，也没有 semantic 路径，最终在预算充足时退出。用归档中的实际 program/facts 调用原始求值与认证函数已离线复现，见 `certificate_deadend_reproduction.json`。例如 `5117e665-5204-44ae-9946-0c984965c04e` 仅用 2 次 LLM、1 次 ANN 就进入此死端。

另一个 determined 病例 `63f0c40f-a1c8-4e5d-af0a-37bc2b317185` 的 `rules_complete=False` 阻止认证。这需要在规划时解释如何补全规则，而不是把认证保护直接取消。

对全部 23 个完整初始计划重放生产 `validate_plan`，23/23 均被接收；原求值器的状态与日志也 23/23 一致。剩下 11 个 indeterminate 病例进一步分为：8 个原文/父事实/反证超过实际输入容量、1 个 compose 缺少原始来源、2 个把未来保密建议当作必须从历史找到既有保密策略而无法组合。它们仍有 ANN/LLM 配额，不能用笼统“预算不足”解释。

修复校验必须保留合法边界：带 rule_binding 的初始 var 可以在找到来源规则后被实例化，不能一刀切拒绝；不完整规则也存在合法的否定见证短路。应验证当前计划是否存在可达的合法完成路径，而非自动改 mode 或把 rules_complete 翻为 True。完整复现见 `contract_deadend_findings.md`、`repro_contract_deadends.py` 和 `contract_deadend_repro.json`。

### E. 审计与其他异常

17 次 audit_incomplete 中，互斥分类为：最终 conflict 8、unknown 1、supported 但仍有义务 1、重复观测 ID 4、text 类型错误 1、LLM 预算耗尽 1、实际输入容量超限 1。审计发现真实矛盾应保留；当前一旦审计返回 false 就结束，缺少有预算时的受限纠错/重新求值路径。

7 次 execution_failed 的错误是：5 次 `Compose requires parents; execution must be retrieval/compose`，1 次终端变量 scope 与不可变契约不一致，1 次 rule_binding 指向非 rule 变量。当前包能确定异常内容，但没有这些失败的 planner 原始响应与 repair 请求，不能进一步断定是首次输出还是修复耗尽。

4 次 timeout 只能确认 worker 超过 3600 秒，不能据现有包分辨服务等待、重试或某段计算。详细列表见 `infrastructure_failures.json`；这个文件名不意味着其中 7 个规划异常属于基础设施故障。

## 为什么有效作答也会退化

已找到“证据实际读到了，最终仍选错”的案例，因此下降不能统一归为召回不足。

符号路径的典型过程是：将问题缩成单一事实变量，读出支持该事实的原文，给这个值生成证书，再把值对应到回应选项。这里可以每一步都符合结构协议，但选中一个缺少用户历史语境的泛化回应。

细读案例涉及 DIY、图书馆和节庆经历：模型读到了与个人反应有关的原文，但计划/审计主要关注物品名、事件或 festival 名称。证书验证的是这些窄事实，不是用户偏好或最终回应的适合性。若 original 的中间节点同样 unresolved，但最终 Reader 阅读更多原文仍答对，差异就不能简单解释成 original 更会拆问题。

语义路径也有时序压缩错误：`f8edd318-d6b7-4943-a60c-c02e54f203d3` 同时读到早先嫌 flashcards 太浅、后来重新采用创意 flashcards 且效果更好的内容，中间 profile 却保留旧结论，影响最终选项。另有找到 hiking club 后组合为 environmental cleanup 的案例，涉及阅读/组合环节；但该题还有受伤后偏好变化的材料，不能把它说成毫无依据的建议或毫无歧义的标注。

反向样例也存在：一些仅抽取一个事实的路径依然选对，并修复了 original 的错误。因此“一变量”不是普遍错误判据。完整案例及相反例由 `effective_answer_findings.md` 记录；案例阅读是机制诊断，不是每类根因的全量频率估计。

## 旧 reranker 版本：用户记忆成立，但不能当单因素实验

旧归档 `dagv2_results_20261008_025515.tar.gz` 的 20 个 dagbt 源哈希对应 `774d285`。这是 HotpotQA 1000 题中已导出 951 题的快照。

| 旧 HotpotQA 口径 | original | 旧 fusion |
| --- | ---: | ---: |
| 共同成功 704 题 EM | 411/704 = 58.38% | 446/704 = 63.35% |
| 共同成功 704 题 F1 | 73.02% | 76.85% |
| 全部已导出 951 题 EM，失败计 0 | 565/951 = 59.41% | 447/951 = 47.00% |

所以，旧版本在共同成功题上 EM 确实提高 4.97 个百分点；它同时也有 246 个失败，主要为旧 FinalSelector 的固定头部与 disputed source group 协议。共同成功收益不能外推为修复全部失败后的整体收益。

当前 residual 同时改动了：

1. 去掉原问题的全局 dense 候选入口，转为 active local demand 的检索。
2. 去掉 scored activation，以及依赖分数的 pair/speculation/pivot 等搜索机制。
3. 去掉 FinalSelector/raw review 的全局文档重选。
4. 去掉独立 Reader，改由指定 DAG terminal 输出。
5. 加入 typed variables、joint reading、residual scheduling 与严格 audit/输出契约。

这不是保持其他条件不变的“只关 reranker”。此外任务从多跳事实问答变成个人记忆的回应选择，评分也从 EM/F1 变成选项 accuracy。两边声明的模型 ID 一致不能证明跨日期服务权重/模板完全一致。旧包没有完整检索和请求 trace，无法进一步分离 reranker 的实际贡献。

original 的冻结核心 57 文件没有变化。当前两臂上游都不见选项，选项分别在独立 Reader 或 residual terminal 才出现；因此不能把当前两臂差距简单解释为 baseline 提前看到了选项。两臂预算机制不同：original 用 `Ledger({})`，residual 受 24 次 LLM 等限制，但原方法实际平均调用更少。

## 建议的处理顺序

1. **先修确定的协议/控制缺陷。** 在规划接收时联合校验契约、表达式和补全规则的可行性；在状态中保留 typed value，展示字符串只用于展示；提前检查终端多个字段的一致性并有界修复；识别相同证据/状态下无进展的重复读取；审计产生反证后在预算内允许重新求值与修复。
2. **再修任务目标。** PersonaMem 的终端需要完成“基于个人历史选择合适回应”。把必要的历史事实作为中间变量，不能让一个物品名/事件名的事实证书替代最终任务，也不能在只支持个人记忆检索时强制寻找外部新书目录或实时活动清单。模式与需求应依据公开任务定义判断，不依据正确选项修改。
3. **同数据集恢复对照，定位 reranker。** 先让旧 scored fusion 在当前 PersonaMem 输入适配下可靠运行；在同一 planner、终端 Reader 和预算下比较有/无评分引导，再比较修正后的 residual。评分引导涉及一组联动搜索机制，现有 proxy-free 不是一个完全隔离的单模型删除。恢复独立 Reader/全局证据重选应单独对照，不能与加回 reranker 一起改后把全部增益归给它。

当前不建议只把 ANN 或 LLM 配额加大后直接重跑全量，也不建议绕过审计、抹去未知状态或将失败移出分母。上述修复能否提升正确率需另行实验；本报告没有给出修复后的虚构成绩。

## 成本观察与验证边界

已记录 445 题，平均 wall time 为 original 16.44 秒、residual 181.31 秒；对应观测 token 总量约 1293 万和 2476 万。辅助 tokenize 另计：original 2074 次 HTTP，residual 185104 次 HTTP，后者记录约 7816 秒接口耗时。这是优化优先级的额外信号，不是答案错误的因果证明；网络等待、缓存、超时以及缺失返回 usage 会影响成本解释。

本次没有进行 reranker 因果消融，没有对全部语料标注证据相关性，没有用模型重答题，也没有改写失败记录。修复候选来自协议和轨迹分析；现有标签用于核算与错误检查。后续若基于这些样例调整方法，应保留本轮原始分数，并另用未参与调试的保留数据验证泛化。
