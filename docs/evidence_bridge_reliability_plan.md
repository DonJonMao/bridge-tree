# Evidence BridgeTree 运行可靠性修订计划

日期：2026-09-27。状态：2026-09-27 按本方案实施 v2；验证结果由 evidence_bridge_v2_validation.md 维护。本轮按用户指示优先修复引用与 JSON 协议，允许通过截断处理新证据模块的输入超长，并检查跨需求引用规则。本文对“允许截断”的约定取代 v1 设计中相关的禁止截断条款；实施时同步更新正式方法文档和版本标识。

## 1. 依据与范围

服务器当前已处理 283 个 evidence_bridge 任务：53 成功、230 失败。失败为 201 次 EvidenceValidationError、28 次 EvidenceInputBudgetExceeded、1 次 EvidenceSelectionInfeasible。前五类为引用不匹配 102、JSON 开头无法解析 49、输入超预算 28、引用超过 400 字符 15、跨需求引用 13，合计 207 次。

这些是当前权威 outcome 的终止错误计数，不代表任务内所有失败尝试，也不能用来认定具体语义错误。尚未取得这轮完整原始模型响应。已展示的三条输入错误属于 evidence_select；其余 25 条仍需按阶段核查。49 条 JSON 开头错误不是已确认的空响应：当前 client 在 JSON 解析之前就拒绝空白 content。

本轮修改集中于证据层：引用表达、结构化响应、局部恢复、证据选择输入截断及需求关联。保持当前搜索调度、activation 四项测量、target retain/speculate/pivot 与 reader 任务定义，便于从下一版日志判断此次修复的作用。旧 embedding/reranker 物理超长专项继续暂缓。

## 2. P0：统一修复问题 1 和 4——模型选片段，代码提取引用

### 2.1 输入与输出协议

由代码从原始 Memory.text 构建带编号的 source spans，保存原始字符区间、memory/source ID、真实角色与时间元数据。短编号稳定且在一次任务内唯一；批次变化或重试不能让同一个编号指向不同原文。

映射输入展示 `span_id、text、role` 以及必要的上下文；模型输出 `requirement_id、span_ids、claim、kind、relation、time_scope`。不再要求模型复写 quote 或自行计算字符偏移。代码校验 ID 属于本次可见输入，再从 `Memory.text[start:end]` 得到原文引用。

示例输出：

```json
{
  "requirement_id": "r1",
  "span_ids": ["s12", "s13"],
  "claim": "这段历史提供的事实",
  "kind": "explicit",
  "relation": "support",
  "time_scope": "past"
}
```

### 2.2 切分约定

- 优先沿真实 source_segments 的段落或句子边界切分，每个 span 不超过 400 字符；单句过长再切分。原始内容均可参与映射，句段信息与相邻关系保留。
- span 不跨不同说话人的权威区间；结构性间隙或无权威元数据保持 unknown。文本中出现 `Assistant:` 不改变实际角色。
- 一项判断可以引用多个 span，保存为多个原文片段；不把拼接后的引用再强行截头，以免删掉否定或时间条件。
- 同一项判断引用两个片段，仍是一条证据，不能凭切片数量满足“至少两个不同前提”的联合推断要求。重叠片段和重复映射不能制造独立证据数。
- 校验仍拒绝未知 ID、引用本批未展示内容、错误来源和错误角色。由代码提取原文只能保证出处，支持关系与推断语义仍需模型判断。

预期：合法 span 引用在构造上不会再触发“模型 quote 与原文不一致”或“单片 quote 超过 400”。潜在的模型错选 span 仍需显式校验，不能当成已解决所有证据语义错误。

## 3. P0：修复问题 2——JSON 协议与局部恢复

### 3.1 先识别错误种类

从 client 向证据模块传递原始 content、finish_reason、拒答标记（服务提供时）、实际 usage、响应 ID 与实际输出协议。缺失元数据保存 unknown，不推断为正常结束。兼容既有测试后端返回纯字符串，实际服务优先提供带元数据的响应。

区分包装问题、JSON 语法错误、明确输出截断、schema 错误、证据关联错误和 HTTP/网络故障。`finish_reason=length` 才明确记为输出长度截断；仅语法缺尾时先记 suspected。

### 3.2 输出约束与解析

- 为 evidence 调用单独配置 plain/json_object/json_schema 模式。先核实当前兼容服务的能力，再固定本次 run 的模式，模式与 schema 版本进入运行身份。最终 reader 不继承 evidence 的格式约束。
- 先从 49 条真实失败中识别实际包装形式。解析器可去除完整 BOM/代码围栏等确定包装；若允许解释前后的 JSON 提取，只接受唯一、完整的顶层对象。
- 保留重复键、NaN、多个竞争对象、不完整 JSON 的拒绝规则。不能靠自动补括号、字段或数组项制造“成功”。
- 遇到明确输出截断，优先减小当前映射批次与输出负担；不把它当成普通枚举错误反复发送同一大请求。

### 3.3 修复粒度与额度

建议初始配置：每个逻辑请求最多两次修复，整题最多六次修复，全部计入现有最多 24 次 evidence 调用。给首次整体选择及 reader 预算修订保留调用额度；映射不能用尽所有调用后再发现无法选择。

- 完整 JSON 已解析时，按 unit/assessment/coverage 行校验并收集错误；保留有效行，只重新请求失败部分。
- 错误反馈包含具体字段路径、失败 ID、当前需求与允许引用的 ID 集合。修复只携带相关原文和必要约束，不不断追加整份错误响应。
- JSON 不可解析时无法安全保留其中半条事实，才重做或拆小当前批次。
- 有限修复后仍不可用的条目标为 unassessed/unavailable；有合法证据的部分可以继续。不得将未评估条目记为无关，也不得把部分映射记为完整覆盖。
- 拆开 `fully_mapped_ids` 与“已有有效证据可参与选择”的候选集合，防止局部恢复后被旧的全量映射门槛再次拒绝。
- 若最终没有任何合法选择响应，则仍明确报告失败；不能把伪造证据或无效 JSON 当成正常完成。服务不可用等外部故障继续按原有重试规则处理。

目标是使局部可恢复错误不再轻易废弃整题，不承诺任何服务条件下零失败。

## 4. P1：按授权截断证据选择输入

采用确定性、按完整记录截断的方式，先保证证据层请求能够进入配置预算。此修改明确改变 v1 的“全部 ledger 一次输入”规则；结果与日志必须能识别这个变化。

### 4.1 截断位置

优先在 `evidence_select` 的 payload 组装阶段控制长度，针对证据表以及随其变化的 candidate_costs/候选清单。不是对序列化后的 JSON 字符串直接切片，也不是随意改写原始 Memory、需求或最后 reader 输入。

映射仍按输入预算分批；问题 1/4 的引用片段预切分属于来源协议，不与选择阶段的证据条目删减混淆。确认其他 25 次输入异常的阶段后，再覆盖必要的修复请求预算边界。

### 4.2 保留顺序

1. 固定保留原 query、冻结需求、schema 和必要预算信息。
2. 按必要需求轮转分配证据条目，先使每个有证据的必要需求得到展示机会，再逐轮添加；随后处理可选需求。每组使用稳定次序，并尽量避免一个 memory 的多条重复映射占满输入。
3. 在实际序列化输入的估算预算内保留完整条目；同等条件下先去重重复记录，不额外引入 R 排名或新的语义打分器。支持、矛盾与历史阶段信息保留原字段。
4. 根据本轮保留证据同步建立 `visible_evidence_ids`、允许的候选集合及成本信息。选择器只能引用本次确实展示的证据，不能凭历史别名引用已被裁掉的行。

如固定 query/需求/schema 本身已超上限，删减证据无法解决，应单独记录为不可裁剪输入超限。预算留余量，repair 的附加字段同样纳入检查；本地 token 仍是估算，不能承诺服务端 tokenizer 必然接受。

### 4.3 必须保留的诊断

记录截断前后估算 tokens、条目数、候选数、保留/删除的真实 IDs、每个需求的保留情况与截断策略版本。完整映射结果仍在 artifact 中保存。区分“没有找到证据”和“有证据但本轮预算未展示”，不能让截断造成的缺口冒充检索缺失。

本轮允许用此方案换取可运行性。它可能损失有用证据，后续效果分析应能单独查看发生截断的任务。

## 5. P1：先修已确认的问题 5 契约缺口，再检查真实语义

已确认：SELECT_PROMPT 要求引用 ledger IDs，但没有明确规定“coverage 只能引用相同 requirement_id 的证据”；校验器却强制此条件。模型当前还需从平铺表中复制带 20 位哈希的证据 ID。mapping 本身允许同一原文分别映射多个需求，因此并非方法禁止证据复用。

立即可规划的最小修改：

- 明确写出相同需求规则；按需求分组提供允许引用的证据，使用 `r1_e1` 等短别名，代码映射到持久化 evidence ID。
- 给模型一个“同一 memory 支持两项需求、分别使用各自映射行”的例子。
- 局部错误反馈准确指出 coverage 需求、被引用证据的需求和可用替代 IDs；其余合法覆盖行不重写。
- 保留跨需求检查。未经重新映射，不自动把需求 A 的 support/explicit 标签迁移到需求 B。

检查全部 13 个真实失败：

| 分型 | 判据 | 对应处理 |
|---|---|---|
| ID 错引 | 目标需求下已有正确证据行，却引用了另一需求的 ID | 分组、短 ID、局部修复 |
| 映射遗漏 | 原文确实支持该需求，却没有相应映射行 | 对指定原文和需求补映射，再参与选择 |
| 语义越界 | 原文并不能支持该需求 | 保留拒绝，报告 missing/partial，必要时补检索 |

所需材料：冻结需求、失败 select/repair 的原始输入与输出、错误字段、被引用及可能替代的 ledger 行、对应原文。这部分目前只有错误统计，不能先判定 13 次都是同一种原因。

## 6. 实施顺序与文件

1. 取得现有失败 artifact，按阶段和错误分组；抽查 JSON 开头/缺尾样本，并逐项核对 13 次跨需求错误。
2. 引用协议改为 span ID，补 source/角色/字符边界与多片段证据校验。
3. 新响应元数据、受控 JSON 解析、局部修复和全局额度；同步拆开候选完整性与可选择资格。
4. 选择输入按记录截断，按需求分组与短证据别名，同步显式覆盖/截断状态。
5. 更新模块日志、汇总、方法契约与运行版本，完成验证后再部署。

主要文件：`evidence_selection.py`、`clients.py`、`evidence_config.py`、`dependency_config.py`、`dependency_experiment.py`、`diagnostic_observability.py`、`evidence_diagnostics.py` 及相关配置、测试、文档。涉及服务元数据时配套更新 `request_audit.py`。不借此次修复重写搜索策略。

## 7. 验收与结果解释

- 来源验收：中文/英文/emoji/换行、长句、跨片段否定与时间条件、不同说话人的重复原文、尾部证据，引用均能回到准确原文；未知和不可见 ID 继续拒绝。
- 恢复验收：从真实失败响应建立离线 fixture，覆盖已确认的包装、语法与截断类型；一条坏 assessment 不损失有效行；修复不改变有效出处；局部/全局预算可核对。
- 截断验收：超过 16,384 的选择输入在进入调用前被裁至预算，最终输入仍是合法完整对象；所有被引用 ID 都实际可见；删除条目和受影响需求可追溯。
- 问题 5 验收：同源多需求映射可正确使用；跨需求错引仍拒绝；补映射不能直接复制旧需求的语义标签。
- 流程验收：正式 executor 贯通 planner、搜索、部分有效证据、选择与 reader；成功但发生部分丢弃/截断的任务应标明降级原因，汇总分别统计正常完成、降级完成、真实失败及各自准确率与成本。
- 最终检查实际服务的结构化输出兼容性和代表性失败样本，不能只用理想格式的测试替身认定真实稳定性达标。

新协议、截断策略和预算进入新版本与运行身份。修复后新建 run，不向旧运行目录混写不同方法的结果；旧日志保留用于对照。本文件保留设计动机与拟定验收口径；实际实现差异、验证和部署产物以 evidence_bridge_v2_validation.md 为准。
