# 当前 v2 实验：真实日志结论与修改建议

2026-09-30。本文基于新收到的实际 v2 导出，替代 [导出前的初步判断](REPORT.md)。本审计阶段只读，未修改实验源码或配置，也未发送模型请求；随后授权实施的 v3 改动及真实开发烟测另见 [v3 验证记录](../../docs/evidence_bridge_v3_validation.md)，不与本次 v2 统计混合。

## 核心结论

**dense 确实向最终 reader 提供更多原文；Evidence Bridge 则花费更多计算，将大量原文过滤掉。主要过滤点已经定位到“需求规划 → 证据映射 → 可选资格”，并非最后的 selector 或 reader 容量。** 逐题原始响应确认，某些已召回的关键历史被不合适的需求或错误的无关判断排除了。

修改优先级应相应调整：先纠正个性化任务理解、检验映射否定判断的淘汰权限；保留 dense 原文作为独立消融，不直接宣布并集是最优新方法。暂不增加搜索复杂度。额外搜索存在补回相关历史的实际例子，但尚未证明其对答案的因果收益，不能笼统宣布搜索完全无用。

73 题的 dense 原文共 876 条，全部进入 EB 候选池，全部完成映射处理：

```

  → 208 条得到有效映射并进入 eligible
  → 194 条进入最终 reader
```

总共丢弃 682 条：668 条在映射到 eligible 的阶段失去资格，只有 14 条是已有资格后没有被选中。也就是 **97.95% 的原文丢弃发生于映射资格判断**。这不表示所有 668 条都有用或都被误判，但明确了应优先检查的位置。

## 获胜案例对“保留 dense 就更好”的限制

两个 normal EB 独对案例均未证明复杂搜索补回了决定性缺失历史：

- 冥想/暑期辅导 `56fb1ba3`：30 候选、260 个单元全部评估，但 0 映射、0 选中记忆。规划要求项目名称、年份、学校等，完全遗漏冥想偏好。最后 reader 只看问题和选项答对。保留 dense 原文将恢复当前已记录的 dense 错误输入；不能保证只救 loss、不损伤 win。
- 烹饪课 `8f6defba`：关键“以前喜欢烹饪课”的 m02 本来就是 dense 第一名。EB 留下它和一条一般背景后答对，可能与上下文精简有关，但未排除 reader 波动；不是首次找回关键历史。

## 成本：已经可以排除 dense 总计算更多的解释

normal 73 题中，EB 每题平均 34.86 次检索、346.68 个逻辑评分集合、186.30 次 reranker 传输，另有 20.60 次证据 LLM 调用。证据请求共 1504 次，全部有服务 usage，每题平均 **99,736 输入和 15,121 输出 tokens**，这还不包含最后一次 reader。

EB 775.6 秒对 dense 24.9 秒约为 31.2 倍任务耗时，不能称为 31.2 倍货币费用。机器资源和 token 单价未知，本文不换算金额。reader token 为本地估算、证据 usage 为服务计数，也不混用两种口径计算精确费用倍数。

dense 的耗时还包含共同记忆库首次 embedding；EB 在这些同题里全命中该缓存，也从先跑的 activation 评分缓存受益。因此目前的成本归因并没有给 dense 隐藏额外预算优势。

成本计数缺陷已实测确认：**177/177 个 EB outcome 的顶层 `costs.evidence_calls` 为 0，而正确的 `costs.evidence_reasoning.evidence_llm_calls` 全部大于 0**。分析使用后者并核对真实 requests。详见 [成本报告](cost_actual.md)与[可复现脚本](cost_actual.py)。

## 剩余执行失败：发现一个可直接修复的预算缺口

31 个 EB 终止失败均为 `EvidenceValidationError`。错误模式可重叠：26 个包含 inference 被标作 explicit，7 个引用选集外证据，5 个跨需求引用，1 个 kind 非法。

其中 9 个任务首次 selection 校验失败后，没有发送任何 selection repair。我按当前源码与原始 payload 离线重建：原始错误 9/9 精确复现，加入固定选集的 `repair_scope` 后，即使将错误反馈缩到代码允许的最短长度，完整修复输入仍为 **16409–16552 tokens，超过 16384 上限**。原 selection 输入约 16040–16127，固定预留的 256 不够，代码遂重新抛出原来的关系错误。因此它在最终汇总里没有显示为输入超限，容易误以为修复已经尝试但无效。

修法应是按实际 repair envelope 计算预留，或构建仅含待修需求及合法证据的局部修复输入，同时保留已验证状态和引用约束。简单扩大全局调用次数不能解决这个容量问题。这个修复能恢复尝试修正的机会，不保证这 9 个任务都会成功。

另一个明确修复是登记原生 evidence 调用的计数。两者都应独立于方法消融，避免把执行成功率改善当作语义方法收益。[离线预算重建结果](repair_budget_reproduction.json)。

## 建议的下一步顺序

1. **可靠性修复单独提交与验证**：修复局部修复输入预算、原生调用计数；继续保留真实失败与覆盖状态，不把不合规证据伪装成成功。
2. **先做任务定义修正的单变量实验**：planner/mapper 明确服务于基于用户历史的个性化回复。用户近况陈述不自动生成名称/时间/地点查询；推荐任务需用户口味，不要求记忆已包含推荐答案。需求仍只看 query，不输入 gold，也不临时让某一种方法读取选项。避免对所有题硬套历史原因模板。
3. **另做映射淘汰权限消融**：原始 dense 召回作为可用的信息来源，不因一次无关判断就永久排除。先用现成 D、S 与同预算并集验证保护原文的收益/干扰，再决定是固定保留、候选保留加原文复核，还是更有限的否定判断复核。绘画案例表明仅修 planner 仍不足够。
4. **补充无历史对照**：与 D、S、D∪S 使用同一个 reader/选项，区分问题和选项本身可答、上下文精简收益、额外召回收益。对固定输入安排预定重复，避免只展示单次被救回的题。
5. **搜索改动后置**：先量化初始桥接、复杂条件搜索、定向 gap 各自带来的决定性新增证据，暂不扩大预算。既不把搜索次数当效用，也不因平均表现差就删除已经观察到的有效补检路径。

当前 7 个 normal 差异题用于定位；全部已完成配对题用于开发检查。最终版本应在未用于调参的预留题或独立数据上确认。主要结果仍报告所有任务的准确率、失败率、费用/耗时，normal 与空证据组作为补充诊断。

**当前最具体的修改目标是：纠正“需要什么个人历史”的任务理解，并减少错误映射否定导致的原文淘汰。** 实际日志已经足够确定这个优先级；还需要受控干预来决定哪种保护策略能带来稳定净收益。
