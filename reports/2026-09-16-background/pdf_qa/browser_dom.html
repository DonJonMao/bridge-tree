服务器一键后台诊断

BridgeTree · PR1–PR4 · 2026-09-16 操作补充

本服务执行无训练诊断，不更新模型权重。默认是 28 个集合评分、310 个生成 trial 和 12 次根顺序搜索消融；不是原 589 题 × 5 方法全量评测。

首次上传与配置

上传完整源码，不上传本机虚拟环境。服务器须有 Python ≥ 3.9 和 venv；另行放置两份 chain-audit 归档，以及相同 revision 的 PersonaMem-v1 32k questions / shared_contexts 文件。

cp configs/diagnostic_28.yaml configs/diagnostic_28.server.yaml

编辑 server 副本的归档和数据路径；相对路径按 YAML 所在目录解析。保留归档 SHA。根据部署示例创建私有覆盖文件，将 deployment_override 指向它，填写三个服务的真实 endpoint、模型与部署 revision / 身份来源。未知身份不能编造。

准备好配置后，一条命令启动

bash scripts/start_diagnostics_linux.sh   configs/diagnostic_28.server.yaml

首次自动创建独立 .venv-diagnostics，安装基础依赖，然后启动独立会话中的后台管理器与工作进程。命令返回后可以退出 SSH；不需要再加 nohup 或 &。安装完成、后台启动信息返回之前，仍须保持终端连接。

新运行自动冻结输入与调用预算，按历史分析 → 新评分 → 重复生成 → 事后评价 → 根消融 → 报告执行。正式模型调用前核对三个服务身份。门禁失败会保留失败状态，不冒充实验完成。

仅检查离线链路

bash scripts/start_diagnostics_linux.sh   configs/diagnostic_28.server.yaml --offline

离线模式不发 embedding、reranker 或 generator 请求；它不验证真实服务连通性。完整准备步骤见 docs/diagnostic_runbook.md。

后台管理与续跑

日常命令：在仓库根目录执行

bash scripts/run_diagnostics.sh status
bash scripts/run_diagnostics.sh log
bash scripts/run_diagnostics.sh module-log --module selection
bash scripts/run_diagnostics.sh module-log --module activation
bash scripts/run_diagnostics.sh stop
bash scripts/run_diagnostics.sh resume

log / module-log 使用 tail -F 持续跟踪。Ctrl-C 只退出日志查看，不停止后台任务。stop 验证登记进程身份后请求优雅中断；等待 status 进入终态再 resume。

续跑不等于重新测一遍

同一 manifest 下成功 trial 和终止失败直接恢复，未用完且允许继续的尝试才续跑。物理请求额度从持久记录恢复，不因重启清零；错误答案不触发重试。若需要新增实验，应使用新目录重新冻结，不能覆盖旧结果。

离线创建的运行，若配置与身份本来就已冻结为可执行部署，可显式 resume --online。若补填身份或修改了源码、配置、数据，必须新建运行，不能靠 resume 绕过漂移门禁。

路径与状态

默认状态目录：outputs/background-diagnostics
默认运行目录：outputs/diagnostics/diagnostic_时间_随机ID
固定总日志：outputs/background-diagnostics/diagnostics.log
运行目录指针：outputs/background-diagnostics/diagnostics.run_dir

可用 DIAGNOSTIC_STATE_DIR / DIAGNOSTIC_RUN_ROOT 指定独立目录，BRIDGETREE_VENV_DIR 指定 bootstrap 环境。启动输出包含带实际路径、运行 Python 的完整管理命令；自定义路径时直接复用它们。

保护边界：活跃任务不重复启动；坏状态、残缺虚拟环境和安装锁保守拒绝。后台脱离终端不等于开机自启，也不能绕过集群调度器或系统强制清理策略。

四条诊断路线

  1. 候选已在，但被负边际拒绝：对齐 28 格点评分和重复生成。只有补入历史稳定改善回答却降低 R，才形成直接的局部目标错位证据。
  2. 大部分状态围绕少数 target：看 root_coverage 与 max_target_state_share，再比较全部预声明根顺序。低根覆盖不等于其他记忆从未作为 premise 或候选出现。
  3. ANN 多、外部候选多，最终 IDs 仍一样：检查 external_selected_count 与跨 seed 的最终集合 hash。发现候选和使用证据是两个环节。
  4. 任务在生成前 HTTP500：先看请求身份、文档 hash、真实 token 可得性与服务错误。不能归因于生成模型能力，也不能用重试次数当独立样本。

相关性正信号、更多 bundle、更多调用均不是有效性证明。最终仍须用受控反事实和同配置生成验证。

进度口径与本机验收

先看运行，再看效果

run.log / runtime.jsonl 记录阶段、异常和心跳；默认每 5 秒更新 progress.json。心跳只说明进程还能记录状态，不代表请求取得进展。module_diagnostics 汇总已落盘 root 结果；当前正在展开的细节看实时模块日志。

每阶段 success + failed + pending + unknown = planned。这里 success 是程序成功执行，不是回答正确；HTTP 错误是执行失败。started / outcome_unknown 是可重叠的补充指标，不可再次加入分母。

正确性只来自独立 evaluation.json；未执行时准确率为 null，不能报 0%。310 次技术重复来自三个事后案例，不是 310 个独立问题，也不是全量 benchmark 成绩。成本中阶段增量不与总量相加；估算 token 和逻辑输入不冒充账单 token。

终态含义
offline_complete只完成离线分析，线上任务仍待执行
completed冻结诊断阶段均已执行
completed_with_failures流程走完，但存在失败项目，须看明细
interrupted / failed中断或流程故障；保留部分产物
